# Cover_TH (กิลด์ Clover_TH) Backend: เอกสารความต้องการที่ตรวจสอบแล้ว

สถานะ: ฉบับสุดท้ายสำหรับส่งต่อให้ Architect (v5) ผู้จัดทำ: Product Owner (Milo)
เขตเวลาของทุกอย่างในเอกสารนี้: Asia/Bangkok สัปดาห์เริ่มวันจันทร์

ความหมายของป้ายกำกับที่ใช้กับทุกข้อ:

- **[CONFIRMED]** ผู้ใช้/เจ้าของโปรเจกต์ยืนยันแล้ว
- **[DEFAULT]** ค่าเริ่มต้นที่แนะนำ เพื่อให้ออกแบบต่อได้โดยไม่ต้องรอ ผู้ใช้เปลี่ยนภายหลังได้
- **[ASSUMPTION]** สมมติฐานที่ผู้ใช้ยังไม่ได้ยืนยัน ต้องตรวจสอบ (ดูหัวข้อ 12)

---

## 1. ภาพรวมและเป้าหมาย

ชื่อกิลด์คือ **Clover_TH** [CONFIRMED] ส่วนชื่อ repository และโฟลเดอร์โปรเจกต์คือ Cover_TH แอปนี้คือแอปบริหารจัดการกิลด์ Clover_TH ในเกม Ragnarok: The New World (เซิร์ฟไทย) ปัจจุบันมี frontend แบบ React/Vite อยู่ในโฟลเดอร์ `frontend/` ซึ่งทำงานด้วย mock state ในหน่วยความจำทั้งหมด โปรเจกต์นี้คือการสร้าง backend (Node.js, PostgreSQL, Prisma) มาแทน mock state ดังกล่าว

เป้าหมายทางธุรกิจ:

1. จัด Auction ของกิลด์ได้อย่างยุติธรรม โดยผลลัพธ์ถูกบังคับใช้ที่ฝั่ง server
2. ให้สมาชิกลงชื่อเข้าร่วมหรือลา (leave) กิจกรรมประจำสัปดาห์ได้ และทุกคนเห็นรายชื่อ
3. ให้ทีมผู้บริหาร (admin) จัดทีมว่าใครเล่นกับใครในแต่ละกิจกรรม ส่วนคนอื่นดูได้อย่างเดียว
4. ให้สมาชิกเข้าสู่ระบบด้วย Discord เท่านั้น โดย Discord bot ที่มีอยู่เดิมเป็นผู้เพิ่มสมาชิกเข้าระบบ

สิ่งที่ต้องส่งมอบต่อไป: ออกแบบระบบ, ER schema ของ Prisma/PostgreSQL, ออกแบบ API และรายการสิ่งที่ต้องแก้ใน frontend

## 2. ผู้ใช้และบทบาท

| บทบาท | คำอธิบาย | แหล่งข้อมูลจริง (source of truth) |

| Guest | ผู้ใช้ Discord ที่ bot ยังไม่ได้ลงทะเบียนให้ ล็อกอินไม่ได้ | ไม่มี |
| Member | สมาชิกกิลด์ที่ลงทะเบียนแล้ว ลงชื่อกิจกรรม ร่วม Auction และดูแผนทีมได้ | ตาราง Member ที่ bot เป็นผู้สร้าง [CONFIRMED] |
| Admin | ผู้บริหารกิลด์ จัด Auction แก้ข้อมูลสมาชิก แก้การตั้งค่า และจัดทีมได้ | flag admin ใน DB ที่ผู้ใช้ตั้งเอง [CONFIRMED] ไม่ sync role จาก Discord |
| Bot (service) | Discord bot ตัวเดิม ส่งข้อมูลสมาชิกใหม่เข้า backend และรับคำขอแจ้งเตือน | shared secret หรือ API key [CONFIRMED] ว่าต้องมีการยืนยันตัวตนแยกต่างหาก ส่วนกลไกที่แน่นอนให้ Architect เลือก |

ไม่สามารถให้สิทธิ์ admin ผ่าน UI หรือ API ได้ [CONFIRMED] ปุ่ม "grant admin" ใน Admin Config ของ frontend ต้องซ่อนหรือเอาออก

## 5. ความต้องการเชิงฟังก์ชัน

### 5.1 ตัวตนและการลงทะเบียนผ่าน bot

| ID | ความต้องการ | ป้ายกำกับ |
|---|---|---|
| FR-1.1 | ล็อกอินด้วย Discord OAuth เท่านั้น เมื่อสำเร็จ API ส่ง JSON กลับ: member id, Discord id, ชื่อในเกม, ชื่อเล่น, อาชีพ (job), isAdmin | [CONFIRMED] |
| FR-1.2 | เฉพาะสมาชิกที่ bot ลงทะเบียนไว้แล้วเท่านั้นที่ล็อกอินได้ ผู้ใช้ Discord คนอื่นถูกปฏิเสธด้วย error code ที่แยกได้ และไม่สร้าง session | [CONFIRMED] |
| FR-1.3 | สมาชิกใหม่ต้องเข้า Discord server ก่อน จากนั้น Discord bot ตัวเดิมส่งข้อมูลของสมาชิกแต่ละคน (Discord id, ชื่อในเกม, ชื่อเล่น, อาชีพ) มาที่ endpoint ลงทะเบียนของ backend | [CONFIRMED] |
| FR-1.4 | endpoint ของ bot มีการยืนยันตัวตนของตัวเอง (shared secret หรือ API key ใน header) แยกจาก OAuth ของผู้ใช้ ถ้าไม่มีหรือ key ผิดให้ตอบ 401 และไม่เปลี่ยนแปลงอะไร key เป็นค่า configuration หมุนเปลี่ยนได้ และห้ามบันทึกลง log | [CONFIRMED] ว่าต้องมี auth แยก, [DEFAULT] รูปแบบ shared secret |
| FR-1.5 | endpoint ของ bot เป็น idempotent และทำ upsert ด้วย Discord id เรียกซ้ำไม่สร้างข้อมูลซ้ำ | [DEFAULT] |
| FR-1.6 | flag admin คำนวณโดย server จาก DB ห้ามเชื่อค่าที่ client ส่งมา | [CONFIRMED] |
| FR-1.7 | สมาชิกอ้างอิงด้วย id ที่ไม่เปลี่ยน (immutable) ชื่อ (ชื่อในเกม, ชื่อเล่น) เปลี่ยนได้และห้ามใช้เป็น key ปัจจุบัน frontend ใช้ชื่อเป็น key ต้องแก้ | [DEFAULT] |
| FR-1.8 | bot ส่งคำขอ deactivate ได้เมื่อสมาชิกออกจาก Discord server สมาชิกที่ถูก deactivate ล็อกอินไม่ได้ ถูกเอาออกจาก queue, การลงชื่อในอนาคต และการวางทีมในอนาคต แต่ประวัติเก่ายังอยู่ | [CONFIRMED] การเอาการลงชื่อและการวางทีมในอนาคตออก, [DEFAULT] ตัวกระตุ้นจาก bot (O-11) |
| FR-1.9 | สมาชิกถือว่า "incomplete" เมื่อข้อมูลที่ไม่บังคับขาดไป (เช่น ชื่อเล่น) หรือเมื่อ record ถูกสร้างหรือแก้ไขด้วยวิธีอื่น เนื่องจาก job ที่ไม่ถูกต้องจะถูกปฏิเสธตั้งแต่ตอนลงทะเบียน (FR-1.11) flow ของ incomplete จึงไม่ครอบคลุมกรณี job ขาดหรือไม่ถูกต้องอีกต่อไป สมาชิก incomplete ยังล็อกอินได้และถูกติดธงให้ admin ตามแก้ ฟิลด์ที่บังคับจาก bot: Discord id, ชื่อในเกม, job ส่วนชื่อเล่นไม่บังคับ | [DEFAULT] (O-10) |
| FR-1.10 | ชื่อในเกมต้องไม่ซ้ำกันโดยไม่สนตัวพิมพ์เล็ก/ใหญ่ ถ้า bot ส่งข้อมูลที่ทำให้ชื่อซ้ำ ให้ปฏิเสธพร้อมข้อความ error ที่ชัดเจน | [DEFAULT] (frontend บังคับอยู่แล้ว) |
| FR-1.11 | ถ้า payload จาก bot มี job ที่ไม่ถูกต้อง (ไม่อยู่ในรายการ job) ให้ปฏิเสธการเรียกนั้นด้วย error code ที่ชัดเจน ไม่สร้างสมาชิก และคนนั้นล็อกอินไม่ได้ ถ้า payload ไม่ส่ง job มาเลยก็ปฏิบัติเหมือนกัน | [CONFIRMED] job ที่ไม่ถูกต้อง, [DEFAULT] กรณีไม่ส่ง job |

| FR-3.6 | ลำดับ queue ถูก snapshot ตอนเปิดช่วงเวลา คนที่เข้า queue ระหว่างช่วงเวลาจะไปอยู่ท้าย queue และไม่มีสิทธิ์ใน Round นี้ | [DEFAULT] |
| FR-3.7 | ตอนปิด ระบบจัดสรรแยกตามหมวด โดยวนรอบเดียวตามลำดับ queue สมาชิกแต่ละคนได้ไอเทมที่อยู่อันดับสูงสุดในรายการของตัวเองที่ยังไม่มีคนได้ | [CONFIRMED] |
| FR-3.8 | สมาชิกได้ไอเทมสูงสุด 1 ชิ้นต่อหมวดต่อ Round | [CONFIRMED] |
| FR-3.9 | ผู้ชนะทุกคนได้ queue entry ใหม่ที่ท้าย queue entry ใหม่เหล่านี้เรียงกันเองตามลำดับ queue เดิมของผู้ชนะ ส่วนคนที่ไม่ได้ของคงลำดับเดิมและอยู่ข้างหน้า | [CONFIRMED] |
| FR-3.10 | คนที่อยู่ใน queue แต่ไม่ได้ส่งรายการ หรือของที่เลือกถูกคนอื่นได้ไปหมด จะไม่ได้ของและคงตำแหน่งเดิม | [DEFAULT] |
| FR-3.11 | สมาชิกมี entry ที่ active ได้หนึ่งอันต่อหมวด สมาชิกออกจาก queue ได้และเสียตำแหน่ง ถ้าออกจาก queue ระหว่างที่ช่วงเวลากำลังเปิดอยู่ จะเสียสิทธิ์ใน Round นั้น หลังปิดแล้วแก้รายการที่เลือกไม่ได้ | [CONFIRMED] การออกระหว่างที่ช่วงเวลาเปิด, [DEFAULT] ส่วนที่เหลือ |
| FR-3.12 | การจัดสรรต้องกำหนดผลได้แน่นอน (deterministic) เก็บ input (snapshot ของ queue, รายการที่เลือก, ไอเทม) และผลลัพธ์ไว้เพื่อเล่นซ้ำได้ รันสองครั้งได้ผลเหมือนกัน (idempotent) | [DEFAULT] |
| FR-3.13 | ของที่เหลือ (leftover) คือไอเทม type-2 ทุกชิ้นที่จบโดยไม่มีคนได้ รวมของที่ไม่มีใครเลือก และของที่คนเลือกแพ้ลำดับ queue ให้คนอื่นหมด ของเหล่านี้ถูกคัดลอกเป็น Round type-1 แบบ draft ให้ admin ตรวจและกดเริ่ม ไม่เปิดอัตโนมัติ | [CONFIRMED] ของเหลือเข้า type-1, [DEFAULT] แบบ draft และ admin เป็นคนเริ่ม |
| FR-3.14 | ผลลัพธ์ (ใครได้อะไร) เผยแพร่ให้ทุกคนตอนปิด รายการที่สมาชิกเลือกมองเห็นได้เฉพาะเจ้าของและ admin ทั้งระหว่างและหลังจบ Round | [DEFAULT] |

**Golden test (แก้ไขแล้วและผู้ใช้ยืนยันแล้ว):**

| | |
|---|---|
| Queue ก่อนจัดสรร | A, B, C, D, E |
| ไอเทม | 5 ชิ้นในหมวดนั้น หมายเลข 1 ถึง 5 |
| รายการที่เลือก | A = (1, 3), B = (1, 3), C = (3, 2) ส่วน D และ E ไม่ได้เลือกอะไร |
| การจัดสรร | A ได้ 1 (อยู่หัว queue) B: 1 ถูกเอาไปแล้ว ได้ 3 C: 3 ถูกเอาไปแล้ว ได้ 2 |
| ผลลัพธ์ | A: 1, B: 3, C: 2 |
| Queue หลังจัดสรร | **D, E, A, B, C** (ผู้ชนะ A, B, C ย้ายไปท้าย queue ตามลำดับเดิม) |
| ของเหลือ | ไอเทม 4 และ 5 ไปอยู่ใน Round type-1 แบบ draft |

## 6. กฎทางธุรกิจ

1. เวลาของ server เป็นนาฬิกาเดียวที่ใช้กับช่วงเวลา Auction ลำดับการกด ลำดับ queue และลำดับการลงชื่อ
2. ทุกการเขียนตรวจสิทธิ์ที่ฝั่ง server ห้ามเชื่อ role หรือตัวตนที่ client ส่งมา
3. ทุกข้อมูลอ้างอิงสมาชิกด้วย id ที่ไม่เปลี่ยน
4. วันที่ของ Occurrence และขอบเขตสัปดาห์คำนวณเป็น Asia/Bangkok สัปดาห์เริ่มวันจันทร์ เก็บ timestamp เป็น UTC
5. เพดานการกด, ผู้ชนะหนึ่งคนต่อไอเทม, การเลื่อนขึ้นจาก waitlist และ backfill ต้องเป็น transaction (ไม่มีผู้ชนะซ้ำ ไม่มีการเลื่อนขึ้นซ้ำ)
6. การจัดสรร type-2 เป็นฟังก์ชันล้วนจาก input ที่เก็บไว้
7. สมาชิกถือของที่ชนะใน type-1 ได้สูงสุด 5 ชิ้นต่อ Round และชนะใน type-2 ได้สูงสุด 1 ชิ้นต่อหมวดต่อ Round
8. สมาชิกมีสถานะได้ 1 อย่างต่อ Occurrence และอยู่ planner slot ได้ 1 slot ต่อ Occurrence
9. job ที่ยังมีสมาชิกใช้อยู่ ลบไม่ได้
10. การ deactivate เก็บประวัติไว้
11. ความจุของ Room คำนวณจาก Team x ขนาด Team
12. สถานะ admin เปลี่ยนได้ผ่าน DB เท่านั้น

## 7. Edge cases

**ล็อกอินและ bot**
- ผู้ใช้ Discord ที่ไม่ได้อยู่ในกิลด์ หรืออยู่ใน server แต่ bot ยังไม่ได้ลงทะเบียน: ถูกปฏิเสธ ไม่สร้าง session
- bot retry หรือส่งซ้ำ: upsert แบบ idempotent
- bot key ผิดหรือไม่มี: ตอบ 401 ไม่เปลี่ยนแปลงอะไร
- ชื่อในเกมซ้ำใน payload ของ bot: ถูกปฏิเสธ
- payload ของ bot ที่มี job ไม่ถูกต้องหรือไม่ส่ง job: ถูกปฏิเสธ (FR-1.11) ไม่สร้างสมาชิก
- เปลี่ยน Discord username: Discord id ยังเป็น key
- สมาชิกออกจาก server ขณะที่ยังมี queue entry หรือ slot อยู่
- ล็อกอินสองอุปกรณ์ในบัญชีเดียว, session หมดอายุกลาง Auction

**Type 1**
- กดพร้อมกันบนไอเทมเดียว (ได้ผู้ชนะคนเดียว), การกดชิ้นที่ 6, คำขอที่มาถึงหลังปิดเพียงนิดเดียว, กดซ้ำหรือ retry, เน็ตหลุด (เช็กผลของตัวเอง), สมาชิกถูก deactivate กลาง Round, Round ที่ไม่มีไอเทม, admin ปิดก่อนเวลา

**Type 2**
- queue สั้นหรือยาวกว่าจำนวนไอเทม, สองคนเลือกชิ้นแรกเหมือนกัน (ตัดสินด้วยลำดับ queue), ไม่ได้เลือกอะไร (คงตำแหน่ง), รายการที่เลือกมีของที่ถูกเอาไปแล้ว, เข้า queue ระหว่างช่วงเวลา (ไปท้าย queue ไม่มีสิทธิ์รอบนี้), อยู่หลาย queue ต่างหมวด (ทำได้ แยกอิสระต่อกัน), ออกจาก queue, แก้รายการหลังปิด (ถูกปฏิเสธ)

**การลงชื่อและ waitlist**
- ลงชื่อซ้ำ, ลงชื่อ Occurrence ที่ผ่านไปแล้วหรือเริ่มไปแล้ว, คนสุดท้ายที่ joined ยกเลิกแต่ waitlist ว่าง, หลายคนยกเลิกพร้อมกันแต่มีคนใน waitlist คนเดียว (เลื่อนขึ้นครั้งเดียว), สลับสถานะจาก leave เป็น joined (นับเวลาลงชื่อใหม่)

**Planner และ backfill**
- วางลง Team ที่เต็ม, สมาชิกมีสองสล็อต (ถูกปฏิเสธ), วางคนที่ไม่ได้ลงชื่อหรืออยู่ leave (เตือน), ลดขนาด layout ขณะมีคนอยู่ (ถูกปฏิเสธ), admin สองคนแก้พร้อมกัน (version conflict), คนที่ถูกวางถอนตัวขณะ backfill เป็น OFF (ติดธง)
- Backfill: ไม่มีตัวสำรอง (slot ว่าง), ตัวสำรองอยู่ leave หรือถูกวางแล้ว (ข้าม ไปคนถัดไป), คนที่ถูกวางสองคนถอนพร้อมกันแต่มีตัวสำรองคนเดียว (เลื่อนขึ้นครั้งเดียว อีก slot ว่าง), ส่งคำขอถอนตัวซ้ำ (เลื่อนขึ้นครั้งเดียว), คนที่ถูกเลื่อนขึ้นแล้วถอนตัวเอง (slot นั้น backfill อีกรอบ), admin ยกเลิก backfill (คนนั้นกลับไปเป็นตัวสำรองที่ตำแหน่งเดิม), ถอนตัวหลัง Occurrence เริ่ม (ไม่ backfill), แจ้งเตือน Discord ล้มเหลว (การเลื่อนขึ้นยังอยู่ retry ต่อ)
- ผู้ลงชื่อ Guild League เกิน 150 คน หรือ Polarity Zone เกิน 50 คน: ส่วนที่เกินคงเป็น unplaced (ตัวสำรอง)

## 9. ขอบเขต (Scope)

**อยู่ใน scope**
- ล็อกอิน Discord OAuth; endpoint ลงทะเบียนและ deactivate ของ bot พร้อม auth ของตัวเอง
- การจัดการสมาชิก job และกิจกรรม (admin)
- Auction type 1 และ type 2, catalog และ Round ที่ admin สร้าง, Round type-1 แบบ draft จากของเหลือ
- การลงชื่อประจำสัปดาห์พร้อม `leave`, registration capacity และ waitlist (ไม่บังคับ)
- Team planner ต่อกิจกรรม พร้อม layout แบบข้อมูล, Sub room, ตัวสำรอง และ auto-backfill ต่อกิจกรรม
- การแจ้งเตือน Discord เมื่อตัวสำรองถูกเลื่อนขึ้น (ข้อความถึงสมาชิก, โพสต์ใน channel ของกิลด์)
- Audit log พร้อมหน้าดูอย่างเดียวสำหรับ admin
- ER schema, ออกแบบ API, รายการแก้ frontend (สิ่งที่ Architect ต้องส่งมอบ)

**อยู่นอก scope**
- logic ภายในของ Discord bot เอง (คำสั่ง การจัดการข้อความของ bot)
- การ sync role จาก Discord; การให้สิทธิ์ admin ผ่าน UI หรือ API
- Websocket หรือ push ที่บังคับ (polling ใช้ได้ Architect เลือก SSE ได้)
- การแจ้งเตือนอื่นนอกจากการเลื่อนตัวสำรอง (FR-6.6)
- การเชื่อมกับ game client, การรองรับหลายกิลด์, การชำระเงินหรือแลกเปลี่ยน
- ระบบ page hold จาก UI Auction เดิมของ frontend [DEFAULT]
- การอัปโหลดไฟล์รูปไอเทม v1 ใช้ URL ที่ admin วางเอง การอัปโหลดไว้เฟสถัดไป [CONFIRMED]

**สิ่งที่ต้องแก้ใน frontend** (สำหรับรายการของ Architect)
- แทนที่ mock state ด้วยการเรียก API และใช้ member id เป็น key ทั้งหมด
- แทนที่ A/B x 8 x 5 ที่ฝังตายตัวด้วย layout ของแต่ละกิจกรรม (Main/Sub ฯลฯ)
- UI Auction: แทนที่ไอเทมทั่วไป 200 ชิ้นและ page hold ด้วยหมวด, ไอเทมต่อ Round, queue, และการกรอกรายการที่ต้องการเรียงตามอันดับ ระยะเวลาเริ่มต้น 5 นาที
- UI การลงชื่อ: เพิ่มการแสดง waitlisted และตัวสำรอง คง `leave` ไว้
- เอาปุ่ม admin "เพิ่มสมาชิก" และ "ลบสมาชิก" ออก (bot เป็นผู้สร้าง admin ทำได้แค่ deactivate) และซ่อนปุ่ม "grant admin"
- แสดงตัวสำรองและปุ่ม undo auto-backfill ใน planner รองรับห้องที่ว่างเป็นส่วนใหญ่ (Guild League มี 150 slot แต่ roster มีราว 76 คน)
- ล็อกอิน: ใช้ Discord OAuth จริง และแสดงสถานะ error "ยังไม่ได้ลงทะเบียน"

## 10. ข้อกำหนดที่ไม่ใช่เชิงฟังก์ชัน

- ใช้เวลาและการตรวจสิทธิ์ฝั่ง server ทุกที่ การกด การเลื่อนขึ้น และ backfill เป็น transaction
- เป้าหมายโหลด: สมาชิกราว 80 คนกดพร้อมกันระหว่าง Round type-1 [DEFAULT]
- การจัดสรร type-2 เล่นซ้ำได้จาก input ที่เก็บไว้
- การส่งแจ้งเตือนแยกออกจาก transaction ของการเลื่อนขึ้น (FR-6.4)
- API ตอบกลับด้วย error code ที่คงที่ frontend จัดการข้อความไทยและอังกฤษ [DEFAULT]
